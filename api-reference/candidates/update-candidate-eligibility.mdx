## Overview

Flip a single candidate's eligibility — the recruiter's "would I take this person further?" signal, which is distinct from the lifecycle `candidateStatus`. The mutation emits a `CANDIDATE_ELIGIBILITY_CHANGED` audit event with before/after values and returns the updated `Candidate` so your UI can refresh without an extra read. To change eligibility for up to 500 candidates in one call, use `bulkUpdateEligibility` instead; this single-row path exists so the audit operation is logged per row when only one candidate is affected.

<Note>
This operation requires the write scope.
</Note>

## Endpoint

```
POST /graphql
Content-Type: application/json
```

## GraphQL Mutation

```graphql
mutation UpdateCandidateEligibility($input: UpdateCandidateEligibilityInput!) {
  updateCandidateEligibility(input: $input) {
    id
    name
    email
    jobId
    organizationId
    eligibility
    candidateStatus
    verdictId
    isStarred
    updatedAt
  }
}
```

## Request Parameters

<ParamField body="candidateId" type="string" required>
  UUID of the candidate whose eligibility to update
</ParamField>

<ParamField body="eligibility" type="CandidateEligibility" required>
  The new eligibility decision. Allowed values: `ELIGIBLE`, `INELIGIBLE`, `UNSET`
</ParamField>

<ParamField body="reason" type="string">
  Optional free-text reason recorded alongside the change in the audit trail
</ParamField>

## Error Responses

| Error Code | Description |
|------------|-------------|
| UNAUTHENTICATED | Missing or invalid API key or bearer token |
| FORBIDDEN | The token lacks the write scope required for this mutation |
| BAD_USER_INPUT | `eligibility` is not a valid `CandidateEligibility` value or `candidateId` is not a valid UUID |
| NOT_FOUND | No candidate with the given id exists in your tenant |
| INTERNAL_SERVER_ERROR | Unexpected server-side failure while persisting the change |
